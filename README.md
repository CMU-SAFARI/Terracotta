# Terracotta: Enabling DRAM Techniques via a Flexible DRAM Interface and Memory Controller

This repository is the artifact for our MICRO 2026 paper. It reproduces the paper's results with a one-command-per-stage workflow. The artifact consists of two experimentation flows:
- Performance & DRAM energy
- Hardware complexity

**Performance & DRAM energy**
We provide [Ramulator2](https://github.com/CMU-SAFARI/ramulator2)-based models of four DRAM techniques (PRADA, MoPAC-C, MASA, and ChargeCache) and a combination of techniques (ChargeCache+MASA) in two forms: (i) Terracotta-based implementations and (ii) custom implementations. These are simulated using 65 workload traces, then parsed into the paper's figures.

**Hardware complexity**
We provide RTL models for Terracotta and custom implementations of the four techniques, synthesized using [OpenROAD](https://github.com/The-OpenROAD-Project/OpenROAD-flow-scripts) synthesis flow on Nangate45 technology.

## Repository file structure

```
Terracotta/
│  # ── Performance & DRAM energy (run from repo root) ──
├── build.sh                       # build the terracotta:latest sweep image + save a tar (podman)
├── run.py                         # run driver: manifest -> per-experiment configs -> execute
├── run_with_slurm_podman.sh       # full sweep on SLURM, each job in a podman container
├── run_with_slurm.sh              # full sweep on SLURM, container-less ramulator2 binary (--no-container)
├── run_with_personalcomputer.sh   # local N-thread run, in a podman container
├── check_progress.sh              # aggregate progress viewer (--watch for a live dashboard)
├── check_run_status.sh            # per-set done/pending/failed status (gate on completion)
├── parse_results.sh               # raw stats -> CSVs (results/csv/) + reports (results/txt/)   [Python env]
├── plot_all_figures.sh            # per-figure CSVs -> figures/ (PDF + PNG)                      [Python env]
├── download_traces.py             # fetch + sha256-verify + extract the traces into ./traces
│
│  # ── Hardware complexity (run from repo root; delegate into RTL/) ──
├── build_hw.sh                    # build terracotta-openroad:latest (OpenROAD + Yosys from source)
├── run_hw_with_personalcomputer.sh  # synthesis run on your machine, podman container
├── run_hw_with_slurm.sh           # synthesis run on SLURM, podman container
│
├── Dockerfile                     # sweep image (builds ramulator2 in-image; no Python inside)
├── base_config.yaml               # base Ramulator2 config template
├── requirements.txt               # Python deps for the local env (matplotlib/pandas/pyyaml)
│
│  # ── Performance & DRAM energy evaluation harness ──
├── techniques/<t>/                # per-technique inputs, one dir per technique
│   ├── manifest.yaml              #   declarative spec: config variants, core setups, mixes, figures
│   ├── *.yaml                     #   baseline + Terracotta + custom config variants
│   ├── mixes/                     #   workload mixes referenced by the manifest
│   └── README.md
├── common/                        # shared harness: manifest, config_gen, execute, status, parse,
│                                  #   derive, figure_csv, latency[_comparison]
│  # ── Plotting ──
├── plotting_scripts/              # plot_setup.py (shared style) + figure9.py … figure16.py
│
│  # ── Sources ──
├── ramulator2/                    # vendored Ramulator2 simulator — build_ramulator2_release.sh
├── RTL/                           # OpenROAD synthesis internals: driver, designs, Dockerfile
├── cgra/                          # Morpher CGRA latency derivation (background; see cgra/README.md)
│
│  # ── Generated data ──
├── results/                       # raw stats + results/csv/ + results/txt/  (gitignored; regenerated by parse)
└── figures/                       # generated figures  (gitignored; rebuilt by plot_all_figures.sh)
```

## Dependencies

### Hardware

We highly recommend a x86-64-based SLURM managed compute cluster (>1000 cores) due to the large number of experiments.

| Resource | Requirement |
|----------|-------------|
| Disk | ≈ 80 GiB for sources, traces, scripts, intermediate, and final results |
| Memory | At least 32 GiB RAM for building and hardware-complexity analyses; around 4 GiB RAM per simulation |
| Compute | Each simulation is single-threaded; the sweep is thousands of independent jobs |

### Software

| Component | Version (reference host) | Used for |
|-----------|--------------------------|----------|
| OS | Ubuntu 22.04.2 LTS | — |
| git, tar, unzip, wget | — | - |
| **SLURM** | slurm-wlm 21.08.5 | cluster run manager — **highly recommended** for the full sweep |
| Python | 3.10.6 | Scripting and automation |
| pip3 | 22.0.2 | Python package installer |
| CMake / gcc,g++ | 3.22.1 / 11.4.0 (C++17) | Compilation toolchains — only for a *container-less* ramulator2 build |
| Podman | 4.5.1 | hardware-complexity flow (and optionally for performance & energy experiments) |
| matplotlib / pandas / pyyaml | 3.9.2 / 2.2.2 / 6.0.2 | Launching experiments, parsing results, and plotting |

> All containerized steps also run under Docker. See [Experiment customization](#experiment-customization).

## Installation guide

### 1. Collect sources

First, download and unpack the source code from [Zenodo](https://doi.org/10.5281/zenodo.21535720) and then initialize the OpenROAD-flow-scripts submodule.

```bash
cd Terracotta
git submodule update --init --recursive RTL/OpenROAD-flow-scripts         # Initialize OpenROAD
```

### 2. Python dependencies

```bash
pip3 install -r requirements.txt          # matplotlib 3.9.2, pandas 2.2.2, pyyaml 6.0.2
```

### 3. Download traces

The following command downloads and extracts the traces from Zenodo for use.

```bash
python3 download_traces.py               # downloads + sha256-verifies + extracts into ./traces
```

### 4. Build sources

#### Performance evaluation

`Ramulator2` can be built in one of two ways.

**Container-less.** Compiles the ramulator2 binary to `ramulator2/build/ramulator2`.

```bash
./ramulator2/build_ramulator2_release.sh
```

**Container.** Builds the `terracotta:latest` image with ramulator2 compiled in-image, and also saves it to `terracotta_artifact.tar`.

```bash
./build.sh
```

#### Hardware-complexity evaluation

We only support a container-based build of OpenROAD for the hardware-complexity evaluation. The following command builds the `terracotta-openroad:latest` image. It includes the OpenROAD + Yosys toolchain (compiled from source) and all RTL designs.

```bash
./build_hw.sh
```

The first build compiles the toolchain from source, so it takes a while (≈ 30-40 mins).

## Running experiments

### Performance & DRAM energy

#### Launching

**Cluster.** We highly recommend using a SLURM-managed cluster (> 1000 cores) to launch and run experiments.

We provide support for both container-less and container runs. The launcher submits jobs throttled under a concurrency cap (`--max-jobs`, default 700 — we use 1000), so it runs for a while. We suggest launching jobs in _detached-mode_ so that progress can be checked by reconnecting. Set the concurrency cap with `--max-jobs`.

```bash
# Container-less path — each job runs the host-built ramulator2 binary (build step 4, container-less):
nohup ./run_with_slurm.sh all --max-jobs 1000 > sweep.log 2>&1 &

# Podman path — each job loads and runs the terracotta:latest container (build step 4, container):
nohup ./run_with_slurm_podman.sh all --max-jobs 1000 > sweep.log 2>&1 &
```

Track progress anytime (read-only, safe after reconnecting):

```bash
./check_progress.sh --watch              # live aggregate dashboard
./check_run_status.sh all                # per-set status; exits 0 only when all sets are DONE
```

> Note that _re-running_ experiments without changing the results directory may result in incorrect
> progress tracking. See [Experiment customization](#experiment-customization) for how to configure
> the results directory.

**Personal computer.** Local N-thread run. We discourage this track due to the long-running nature of these experiments.

```bash
# Container-less path — runs the host-built ramulator2 binary (build step 4, container-less):
nohup ./run_with_personalcomputer.sh --no-container all > sweep.log 2>&1 &

# Podman path — loads and runs the terracotta:latest container (build step 4, container):
nohup ./run_with_personalcomputer.sh all > sweep.log 2>&1 &
```

#### Parsing and plotting

To analyze the data produced, run the following two commands:

```bash
./parse_results.sh                       # raw stats (results/<t>/<c>/stats/) -> results/csv/ + results/txt/
./plot_all_figures.sh                    # results/csv/ -> figures/figureN.{pdf,png}
```

Figures are dumped into `figures/` in both PDF and PNG formats. Latency comparison results are written into `results/txt/latency_comparison.txt`.

### Hardware complexity

#### Launching

Hardware complexity evaluation does not take long, and therefore, a personal computer run is a viable choice.

```bash
# Personal computer:
nohup ./run_hw_with_personalcomputer.sh > hw.log 2>&1 &

# Cluster:
nohup ./run_hw_with_slurm.sh > hw.log 2>&1 &
```

> These wrappers fail loudly if `terracotta-openroad:latest` is missing, so run `./build_hw.sh` first.

Select the SLURM partition with `--partition <name>` (default `cpu_part`), e.g.
`./run_hw_with_slurm.sh --partition cpu_part`. The hardware-complexity run is a single job, so
`--max-jobs` does not apply here.

#### Results

Output are stored in `RTL/results/` (`synthesis_results.csv`, `terracotta_synthesis_results.csv`, and `RTL/results/txt/hw_complexity.txt` with the final overhead numbers).

## Experiment customization

**Performance & DRAM energy** — `run_with_slurm.sh` · `run_with_slurm_podman.sh` · `run_with_personalcomputer.sh`

```bash
./run_with_slurm.sh <technique|all> [OPTIONS]
```

| Option | Default | Meaning |
|--------|---------|---------|
| `technique` (positional) | — | one of `chargecache`, `masa`, `mopac`, `chargecachemasa`, `prada`, `all` |
| `--core-setup NAME` | all setups | run a single core setup instead of all of the technique's setups |
| `--num-expected-insts N` | manifest value | cap instructions per run (e.g. a short pass) |
| `--num-max-cycles N` | manifest value | cap cycles per run |
| `--max-jobs N` | `700` | SLURM in-flight job cap (submission throttle) |
| `--partition NAME` | cluster default | SLURM partition |
| `--qos NAME` | none | SLURM QOS |
| `--trace-dir DIR` | `./traces` | directory of trace files |
| `--result-dir DIR` | `./results` | root of the results tree |
| `--generate-only` | off | write configs (+ the SLURM jobfile) but do not execute |
| `--status` | off | report done/pending/failed instead of running |
| `--ramulator-bin PATH` | `ramulator2/build/ramulator2` | host binary (container-less runs) |

> The substrate is set by the wrapper, not a flag: `run_with_slurm.sh` = container-less on SLURM, `run_with_slurm_podman.sh` = podman container on SLURM, `run_with_personalcomputer.sh` = local.

New workloads (and mixes) can be added by adding their traces to the `traces` directory and adding corresponding entries into `common/mixes`.

Per-experiment specifics for the simulations (config variants, core setups, workload mixes, and the figures they feed) live in each `techniques/<t>/manifest.yaml`, and can be modified there.

**Hardware complexity** — `run_hw_with_slurm.sh` · `run_hw_with_personalcomputer.sh`

```bash
./run_hw_with_slurm.sh [OPTIONS]
```

| Option | Default | Meaning |
|--------|---------|---------|
| `--batch {all,custom,terracotta}` | `all` | which designs: `custom` = baseline arrays + 4 custom controllers; `terracotta` = TerracottaSingleTech; `all` = both + the overhead report |
| `--partition NAME` | `cpu_part` | SLURM partition (SLURM wrapper only) |
| `--result-dir DIR` | `RTL/results` | where the CSVs and `txt/hw_complexity.txt` are written |

**Using Docker instead of Podman**

Podman is the default. To use Docker instead, set the `RUNTIME=docker` environment variable for the build scripts (`build.sh`, `build_hw.sh`) and the hardware-complexity wrappers (`run_hw_with_*.sh`), and pass `--runtime docker` to the performance sweep (e.g. `./run_with_personalcomputer.sh all --runtime docker`).
